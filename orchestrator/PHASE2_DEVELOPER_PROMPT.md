## Overview

Phase 2 expands the core gameplay loop with **building tier progression**, **in-match upgrades**, and a **functional AI opponent** that makes strategic decisions instead of random unit deployments.

This phase transforms Tower Conquest from a static prototype into a playable strategy game with meaningful progression and competitive challenge.

## Phase 2 Scope

### 1. Building Upgrade System

**What to build:**

- Add `tier` property to `Building` component (default: 1, max: 5).
- Implement `upgrade()` method that:
  - Costs `Building.upgradeCost` units from the building's current population.
  - Increases `capacity`, `generationRate`, and `defenseMultiplier` according to the balance sheet (see below).
  - Increments `tier` by 1.
  - Triggers a visual state change (sprite swap or detail layer update).
  - Prevents upgrade if building has insufficient units.

**Balance Sheet (Tier 1-5 Progression):**

| Tier | Upgrade Cost | Capacity Bonus | Gen Rate Bonus | Defense Bonus | Visual Change |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | N/A (Base) | +0 | +0% | +0% | Base sprite |
| **2** | 20 | +10 | +10% | +10% | Added fortifications |
| **3** | 40 | +25 | +25% | +25% | Larger footprint |
| **4** | 70 | +45 | +40% | +40% | Heavy armor plating |
| **5** | 100 | +70 | +60% | +60% | Epic scale, glowing |

**Example:** A Tier 1 Barracks with 50 capacity and 1.0 gen rate upgrades to Tier 2:
- Costs 20 units (building now has 30 units if it had 50).
- New capacity: 50 + 10 = 60.
- New gen rate: 1.0 × 1.10 = 1.1 units/s.
- New defense multiplier: 1.0 × 1.10 = 1.1x.

**UI Integration:**

- Add an "Upgrade" button to the building info panel (visible when a building is selected).
- Display upgrade cost and new stats on hover.
- Disable button if building has insufficient units.
- Show a tier indicator (1-5 stars or numeric label) on each building sprite.

**Testing:**

- Unit tests for upgrade cost calculation, stat bonuses, and tier progression.
- Integration tests for UI state (button enabled/disabled based on unit count).
- Regression tests ensuring upgrades don't break combat or capture logic.

### 3. AI Opponent (EnemyCommander Replacement)

**What to build:**

Replace the current `EnemyCommander` placeholder with a functional AI that:

1. **Evaluates the board state** every frame:
   - Identify player-controlled and neutral buildings.
   - Calculate defense vs. attack potential for each target.
   - Assess current unit count and generation rate.

2. **Makes strategic decisions** based on simple heuristics:
   - **Defend:** If player is attacking a critical building (e.g., Command Center), defend it by holding units.
   - **Attack:** If a nearby enemy building is weak (low defense), send units to capture it.
   - **Expand:** If a neutral building is nearby and undefended, capture it for resource growth.
   - **Upgrade:** If the AI has excess units and a building is close to the next tier, upgrade it.

3. **Executes decisions** by calling `sendUnit(from, to)` with appropriate unit counts.

**AI Difficulty Levels (for future use):**

- **Easy:** AI makes random decisions 50% of the time; otherwise follows heuristics.
- **Normal:** AI follows heuristics consistently; makes minor mistakes.
- **Hard:** AI optimizes for maximum efficiency; upgrades aggressively; predicts player moves.

For Phase 2, implement **Normal** difficulty as the default.

**Implementation Approach:**

- Create an `AIStrategy` interface with methods like `evaluateTargets()`, `decideAction()`, `executeAction()`.
- Implement `NormalAIStrategy` with the heuristics above.
- Inject the strategy into `EnemyCommander` so it can be swapped for testing or difficulty selection.
- Add debug logging to trace AI decisions (e.g., "AI: Attacking Barracks at (100, 200) with 15 units").

**Testing:**

- Unit tests for target evaluation (ensure weak buildings are identified).
- Unit tests for decision logic (ensure AI chooses appropriate actions).
- Integration tests for AI behavior in a full match (AI should win ~50% of the time against a passive player).
- Regression tests to ensure AI doesn't break existing combat or capture logic.

## Questions & Clarifications

**Q: Should upgrades be instant or animated?**  
A: For Phase 2, upgrades are instant (tier increments, stats update, sprite swaps). Animations can be added in Phase 4 (Polish & Launch).

**Q: Can the AI upgrade buildings?**  
A: Yes. The AI should upgrade buildings if it has excess units and the upgrade is strategically beneficial (e.g., upgrading a high-generation Barracks to increase unit output).

**Q: What if the player and AI both try to upgrade the same building?**  
A: Upgrades are per-building, not per-faction. If the player owns a building, only the player can upgrade it. The AI can only upgrade buildings it owns. This is already enforced by the ownership model.

**Q: Should the AI have different strategies for different building types?**  
A: For Phase 2, use a simple heuristic that applies to all buildings. In Phase 3 (Level Design), we can add building-type-specific strategies (e.g., prioritize upgrading Factories to increase heavy unit output).

**Q: How do I test the AI without running a full match?**  
A: Use unit tests to test individual methods (evaluateTargets, decideAction). Use integration tests to run a full match and verify win rate. See the test structure in the File Structure section.
